# Server API (localhost)

The omni server listens on `:8787` (override with `OMNI_ADDR`); the CLI reads the same variable to find it. JSON everywhere.

- `GET /status` → `{"app":"omni","version":"..."}` — identity of the running server. There is one omni-wide hand-bumped version, shared by cli and server, in `version/version.go` (shown in `omni --help`); `omni status` compares the server's against the CLI's own and alerts on mismatch (a stale binary).
- `GET /channels` → `[{"name":"telegram","connected":bool,"bot_username":"..."}]`
- `GET /channels/telegram` → same object, single
- `POST /channels/telegram/connect` — body `{"token":"..."}` optional.
  Token resolution order: request body > `TELEGRAM_BOT_TOKEN` env > `~/.config/omni/config.yaml` (`telegram_token:` key).
  - `200` connected (validates via Telegram `getMe`, starts long-poll, persists intent to SQLite)
  - `400 {"error":"token_required"}` — no token anywhere; the CLI prompts and saves it to config.yaml
  - `401` — Telegram rejected the token
- `GET /pairing/telegram` → `[{"user_id":"...","code":"...","approved":bool}]` — every user who ever messaged the bot: approved (paired) and pending
- `POST /pairing/telegram/approve` — body `{"code":"..."}` → `200` the approved pairing | `404 {"error":"unknown_code"}`
- `POST /pairing/telegram/revoke` — body `{"user_id":"..."}` → `200` | `404 {"error":"unknown_user"}` (revoked users start over: next message issues a fresh code)
- `GET /llm` → `[{"name":"openai","connected":bool,"source":"...","default":bool,"model":"...","effort":"..."}]` — the three providers (openai, claude, gemini); `model`/`effort` are the `omni llm model` picks from config.yaml, omitted when unset
- `GET /llm/{provider}` → same object, single; `404 {"error":"unknown_provider"}` for anything else
- `GET /llm/{provider}/models` → `["model-id", ...]` — the provider's chat models, listed live from its API when an api key is in use (openai filtered to `gpt-*`/`o<digit>*`, gemini to `generateContent` models with the `models/` prefix stripped); `oauth`/`claude-code` sources (no key to list with) and any fetch failure serve the curated `llmFallbackModels` list instead — except openai oauth, which serves `llmCodexModels`: codex on a ChatGPT login accepts ONLY the models from its own `/model` picker (api names like `gpt-4.1`/`gpt-5.1` get a 400 `not supported when using Codex with a ChatGPT account`); codex has no list-models command, so the list mirrors the picker and goes stale — verify with `codex exec --skip-git-repo-check -m <name> "reply with exactly: pong"` — always `200` for a known provider, `404 {"error":"unknown_provider"}` otherwise. Consumed by `omni llm model`, which validates `-m` against this same list and saves the pick as `<provider>_model` (+ optional `<provider>_effort`, low|medium|high, stored but not yet sent to providers) in config.yaml — written only by the CLI, read by the server: `askAPI` uses it over the hardcoded default, and `cliArgs` passes it to the vendor CLIs (`codex exec -m`, `claude --model`, `gemini -m`).
- `POST /llm/{provider}/connect` — body `{"key":"..."}` optional.
  Credential resolution order: request key > vendor CLI creds file ("oauth") > env (`OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `GEMINI_API_KEY`) > config.yaml (`openai_key` / `anthropic_key` / `gemini_key`) > (claude only) a `claude` binary on PATH ("claude-code").
  - `200` connected (api keys are live-validated with a models-list call; persists intent to SQLite)
  - `400 {"error":"key_required"}` — nothing resolves; the CLI prompts and saves the key to config.yaml
  - `401` — the provider rejected the api key

Behavior notes:

- **Telegram answers are gated by pairing** (keyed on the sender's user id, `message.from.id`): an unknown sender's first message gets the full pairing instructions (their id + an 8-char code + the `omni pairing approve telegram <code>` command, mirroring Openclaw's flow); while pending they get a short "awaiting approval" reminder; only approved senders reach the llm answer flow. Pairings live in the SQLite `pairings` table; codes use an alphabet without ambiguous chars (no 0/O/1/I/L) and never expire. Unpaired senders are rate-limited: 3 replies per sender per 10-minute window (then silence — the poller sends nothing for an empty answer), and at most 50 pending pairings total (past the cap new senders get a "busy" notice and no row). The limiter is in-memory; a server restart resets it.

- **Telegram slash commands** (`handleMessage` in server/command.go, approved senders only; registered via `setMyCommands` on every connect — best-effort — so clients show them as a native "/" autocomplete menu): `/new` starts a fresh chat session and **clears the chat view** (silent reply, command message deleted — the pin dashboard shows the switch); `/clear` only clears the view: every message omni sent or received in the last 48h in every approved chat is deleted via `deleteMessages`, the pinned dashboard excepted — visual only, sessions and memory untouched, best-effort and silent (ids tracked in the SQLite `tg_messages` table by the `seen` hook; see [[decisions/telegram-clear]]); `/agent` and a `/sessions` resume tap clear the same way before their own reply; `/agent [@provider] [task]` starts an **agent session** (see the agent-mode bullet; with a task it runs immediately, without it the next message does — an explicit `@openai`/`@claude` overrides the default, `@gemini`/unknown names error out before any session is created); `/usage` shows per connected provider (disconnected ones omitted): omni's own tracked consumption (today + last 7 days: requests, tokens in/out, cost when the provider reported one), the subscription quota windows for oauth claude/codex (claude: `api.anthropic.com/api/oauth/usage` with the CLI's stored token, `anthropic-beta: oauth-2025-04-20`; codex: last `rate_limits` snapshot in the newest `~/.codex/sessions/*/rollout-*.jsonl` — 5h/weekly used_percent + resets_at, fresh as of the last codex run), and this month's billed cost for **admin** api keys (openai `/v1/organization/costs`, anthropic `/v1/organizations/cost_report` — regular keys 401 and the line is silently omitted; response shapes unverified against real admin keys, parsed defensively). Usage rows live in the SQLite `usage` table, written by `recordUsage` on every llm call that reports tokens: api responses (`usage`/`usageMetadata`), claude CLI json (incl. `total_cost_usd` — the only reported cost), codex `--json` turn.completed events. Gemini's bare CLI has no usage output — those calls go untracked; `/crons` lists scheduled jobs with a 🗑 inline-keyboard delete button per job (`callback_data "cron-del:<id>"` — `gatedCallback` routes the prefix apart from session-resume uuids); `/sessions` lists the last 5 sessions as an **inline keyboard** — agent ones flagged 🤖, label = llm-given name or the first message trimmed to 40 runes — and tapping a button resumes that session (`callback_query` in the poller: `answerCallbackQuery` stops the spinner, then `gatedCallback` re-checks pairing and moves the active pointer; unapproved taps get silence); `/pin [full|clean]` toggles the **pinned status dashboard** (server/pin.go): a message pinned in every approved chat whose first line is `▶ <active session> · N running · M unread` (visible in telegram's pinned bar), `full` mode adds the 5 newest sessions with ▶/⏳/✉/· markers. Refresh is **event-driven, no ticker**: `go s.refreshPin()` fires on enqueue/drain-exit/unread-append (queue.go), active-pointer moves (`newSession`, `resumeSession`, `ensureSession`), session naming, and on ConnectTelegram (restart/reconnect re-attach). `refreshPin` serializes under `pinMu`, renders current state (no timestamps — identical state ⇒ identical text) and skips the `editMessageText` when the text matches the per-chat `pinLast` cache; a "message is not modified" error counts as success. Pins persist in the SQLite `pins` table (`chat_id PK, message_id, mode`), so the dashboard survives restarts; toggle-off unpins+deletes best-effort (telegram refuses deletes >48h old) but always clears the rows. Cron agent runs bypass the queue, so they never show as ⏳ running. Anything else goes to the **active session**: agent sessions continue their vendor CLI conversation, chat sessions take the composed-history path below. A plain message starting with `@provider` is the **sticky chat pick**: the active chat session is pinned to that provider (`sessions.provider`, honored by `answerWith`) until `/new` or another pick; bare `@openai` just switches, `@openai <text>` also answers the rest; unknown names error before anything is saved, and inside an agent session the pick errors with a `/agent @provider` hint (an agent session's provider is fixed at creation). Replies over telegram's 4096-char cap are sent chunked at rune boundaries, keyboard on the last chunk.

- **Photos & documents, both directions** (server/media.go, `v0.8.0`): an inbound photo/document update reaches a third poller hook (`tg.file`, sibling of answer/callback, nil-guarded) carrying only metadata (`tgFile{ID, Name, Caption}`) — `gatedFile` checks pairing FIRST (an unapproved sender can never trigger a download), then `saveInbox` downloads via `getFile` + `GET <apiBase>/file/bot<token>/<path>` (the Telegram struct now keeps `apiBase`/`token` for this; getFile caps at 20MB, error surfaced) into `filesDir()/inbox/<timestamp>-<sanitized-name>` — `filesDir()` = `~/.config/omni/files` (dev: `omni-dev`), the one owner-visible omni folder, next to config.yaml (photos: `photo.jpg`; same-second collisions get a counter), and the message flows into the **active session, whatever kind**, as `<caption>\n\n[file: /abs/path]` — agent sessions read the path with their CLI tools, bare chat sessions just see it. Outbound: an **agent** reply line `TOOL:send_file {"path":"/abs/file"}` (contract taught by the workspace seed; `ensureAgentDir` appends the section once to pre-existing CLAUDE.md/AGENTS.md that lack it, owner edits preserved) is executed by `applySendFile` — called from `agentAnswer` (before the assistant AddMessage, so history keeps `📎 sent <name>` confirmations, never TOOL lines) and from cron agent runs; uploads go multipart (`tg.upload`, buffered in memory, telegram caps 50MB) to every approved chat immediately regardless of active/unread (only the text follows unread semantics); `.jpg/.jpeg/.png/.webp/.gif` go as `sendPhoto` with a `sendDocument` retry on failure (>10MB/odd dimensions), everything else as `sendDocument`. Cron tools never run in agent replies. Poller downloads block the poll loop (ponytail ceiling); video/voice/audio/stickers are still dropped.
- **Chat-mode file toolkit** (`v0.9.0`, server/media.go `fileTool` + the `filePrompt` contract injected into every chat prompt beside the cron section): chat llms stay bare, but five `TOOL:` lines run **server-side** so plain chat can do file work without host access leaking into the llm — `write_file {path,content}` (create/overwrite, parents created), `read_file {path}` (content inlined into the chat, capped 8KB at a rune boundary — single-pass: the model uses it on its NEXT turn; ponytail ceiling, add a second llm round if that grates; **text only** — a NUL byte or invalid UTF-8 → `⚠ binary` refusal pointing to analyze_file/send_file, after a real incident where a chat model read_file'd a JPEG and dumped 8KB of raw bytes into the chat, `v0.9.2`), `edit_file {path,find,replace}` (every exact match, count reported, miss → ⚠), `delete_file {path}` (regular files only), `send_file` (same upload path as agent mode), and `analyze_file {path,question}` (`v0.10.0`) — the escape hatch for content the text-only chat llm can never see: it runs a **one-shot fresh-context agent turn** (same machinery as cron agent jobs: `agentProvider()` + `runClaudeAgent`/`runCodexAgent` with empty vendor id, usage recorded, no session rows) asking the agent to read the file and answer the question, and the agent's answer replaces the TOOL line — so "explain this image" works from a plain chat session, no /agent needed (slow: a full vendor CLI run inside the chat turn; the contract tells the model to mention it's taking a look). **All six are jailed to `filesDir()`** (`resolveJailed`, `v0.9.1`): relative paths join it, absolute paths must already live inside, `..` escapes are refused with `⚠ … path outside <dir>` — so chat file work stays inside the one folder the owner can browse, and the inbox lives there too so received files stay manageable. Agent-mode `send_file` is NOT jailed (`resolveWorkspace`: absolute anywhere — the agent has full PC control already; relative → its cwd, the workspace); `sendFile` takes the resolver as a parameter. Lines run in order, so write+send works in one reply. The contract (`filePrompt()`, now a func — it names the live dir) also carries the honesty rule — chat has NO shell/browser/directory access and must point the owner to `/agent` instead of inventing results (born from a real incident: a chat session claimed to create `/home/jv77/sample.txt`, which never existed). `applyTools`/`runTool` now take ctx (the upload needs it).
- **Scheduled jobs + the first tool protocol** (server/cron.go, server/tools.go): the SQLite `crons` table holds jobs (5-field cron schedule, hand-rolled parser — `*`/lists/ranges/steps, dow 0|7=sunday, classic vixie dom/dow OR rule, server-local time). A minute ticker (`runCrons`, started in main.go) fires matches; **missed minutes are skipped** (downtime = classic cron semantics). Kinds: `message` (⏰ text as-is), `prompt` (single-turn persona-aware answer, never touches the active session), `agent` (one-shot fresh-context agent run in the workspace, usage recorded, no session rows). Delivery: proactive `tg.send` to every **approved** telegram pairing (chat id == user id in private chats) via the `Server.tg` reference kept since ConnectTelegram — omni's first bot-speaks-unprompted path. Creation/edit/delete happen through the **tool protocol**: `cronPrompt` injects the live job list + the `TOOL:cron_add/cron_edit/cron_delete {json}` contract into every chat prompt (rides the persona slot, budget-counted), so listing and suggesting need no tool round; `applyTools` executes TOOL lines in the llm reply and replaces them with deterministic confirmations BEFORE the assistant turn is stored — history carries confirmations, never raw TOOL lines. Single-pass by design (`ponytail:` a second llm round only if it ever matters). The old "fresh install sends bare text" degenerate case is gone above `composePrompt` — every chat prompt now carries the tool section. Tools are chat-mode only; agent mode has its own tools.

- **Agent mode** (`agentAnswer` in server/agent.go): the vendor CLI runs **deliberately un-bare** — user settings, MCP and hooks load, so memoria records the session — with full permissions, cwd = `~/.local/share/omni/agent` (dev: `omni-dev`; seeded once with CLAUDE.md/AGENTS.md — persona, browser playbook via playwright-cli + CDP on the shared `chrome-profile/`, LinkedIn draft→approve rule, memoria MCP usage (search before tasks, write_page on durable findings; the MCP is registered in the vendor CLIs by `memoria init/setup`) — never overwritten, so delete the files to pick up a newer seed), 15-min timeout, raw text through (no composed history: the vendor session carries context). Providers: claude and codex only (`default_llm` if claude/openai, else claude; gemini falls back to claude with a note). claude: `claude -p <text> --output-format json --dangerously-skip-permissions [--resume <id>]` — the json result carries `result` + `session_id`, and claude **forks a new session id every resumed turn**, so the returned id is persisted to `sessions.vendor_session_id` each time; `is_error:true` surfaces as a ⚠ notice. codex: `codex exec [resume <id>] --skip-git-repo-check --dangerously-bypass-approvals-and-sandbox --json -o <tmpfile> <text>` — reply from the `-o` file, session id from the `{"type":"thread.started","thread_id":…}` JSONL event. Both exchanges still log to SQLite (naming + `/sessions` listing work). Security posture: an agent session is full PC control gated only by telegram pairing approval — single-owner bot, deliberate. `TestAnswerCLIBare` still locks the **chat** path only.

- The server long-polls `getUpdates?timeout=50` and answers every text message with the **default llm** — one composed text prompt carrying the chat persona (`~/.config/omni/AGENTS.md`, seeded write-once at boot, injected every turn), the long-term memory page and the session history that fits `token_budget` (config.yaml, default 8000 est. tokens), plus the new message; see [[chatbot-memory]]. Every provider path gets the same single text turn. `api_key` sources call the provider API directly with the user-picked `<provider>_model` from config.yaml, falling back to hardcoded cheap models (`gpt-4o-mini` / `claude-3-5-haiku-latest` / `gemini-2.0-flash`); `oauth` and `claude-code` sources shell out to the vendor CLI since their stored tokens aren't usable for direct API calls (gotcha: codex refuses to run outside a trusted/git directory without `--skip-git-repo-check`; its answer goes to stdout, all progress noise to stderr — including an echo of the ENTIRE composed prompt, chat history and all, so `runCLI` logs full stderr server-side but surfaces only its last line in the user-visible error; anything more leaks the conversation into the chat as a `⚠` notice). **Every CLI runs bare in chat mode** (`cliArgs` in server/answer.go, contract locked by `TestAnswerCLIBare`): no MCP servers, no user config/settings/hooks, tools disabled or read-only — the host's agent setup must never leak into chat answers. Agent sessions are the sanctioned exception (see the agent-mode bullet). Per CLI: codex `--ignore-user-config -s read-only` (shell tool can't be disabled, only sandboxed); claude `--tools "" --strict-mcp-config --setting-sources ""` (prompt must come *before* `--tools` — it's variadic); gemini `--allowed-mcp-server-names omni-none -e none` (the allowlist rejects empty names, so allow a name that can't exist; built-in read tools have no disable flag). Chat claude/codex additionally carry structured-output flags (`--output-format json` / `--json -o <tmpfile>`) purely so `/usage` can record tokens — they do not loosen the bare contract. A faster direct-HTTP route for openai exists but is deliberately deferred — see [[openai-codex-backend]]. While an answer is being produced the bot shows the telegram "typing…" indicator (`sendChatAction` re-sent every 4s — telegram only shows it ~5s per call). No usable llm (no default, or default disconnected) → the bot replies with a `⚠` error notice, never silence. The old rune-reverse echo is gone.
- Connected state lives in SQLite (`channels` table) as *intent*: on restart the server auto-reconnects if the token still resolves. Live status reported by the API is whether a poller is actually running.
- The token is never stored in SQLite — only env/config.yaml, so the secret has one home. Same for llm api keys.
- `OMNI_TELEGRAM_API` env overrides the Telegram API base URL (used by the e2e smoke test with a fake Telegram); `OMNI_OPENAI_API` / `OMNI_CLAUDE_API` / `OMNI_GEMINI_API` do the same for the llm providers (tests only).
- LLM "oauth" = reusing the login a vendor CLI already stored: `~/.codex/auth.json`, `~/.claude/.credentials.json`, `~/.gemini/oauth_creds.json`. Presence+parse check only — no live probe or refresh; that's the vendor CLI's job. omni implements no OAuth flow itself.
- An llm provider is `connected` when the user connected it (intent in SQLite, `llm:<name>` rows in the `channels` table) AND its credentials still resolve; `source` always reports what would be used right now. The telegram answer flow consumes the default provider (see the first bullet).
- LLM providers have no poller, so a server restart needs no resume work for them.
- The default provider lives in config.yaml (`default_llm`), written only by the CLI (`omni llm set-default`); the server just reads it into the `default` field. With no `default_llm` set and exactly one provider connected, that one is reported as the implied default (computed, never written — it adapts when a second connects or creds vanish). It may point at a disconnected provider — deliberate (e.g. config.yaml copied to a new PC); `omni doctor` flags that. Backup story: config.yaml alone carries the keys + the default.
