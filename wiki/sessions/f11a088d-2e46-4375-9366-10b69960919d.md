# Background per-session task queue + version-bump rule (2026-09-02, 14:02–16:42)

Opened with a concrete ask, refined by exploring the codebase before building: "a long agent execution [was] blocking the telegram... dispatch a long task/long message and... start another session while the first one is running. After the ending i'll receive just a notification message that the task has finished, when i change to that session i recover the latest answer." This was the exact deferral already flagged as [[tasks]] item #1 ("unblock the serial telegram poller") and the `ponytail:` comment already sitting at the block point in `telegram.go`.

Two Explore agents mapped the whole synchronous chain end to end (`Poll` → `t.answer` → `handleMessage` → `agentAnswer`/`ChatAnswer` → `runCLI`, the single global `active` session pointer, the existing `digesting atomic.Bool` in-flight-guard idiom, and the cron `notifyOwner` proactive-send path as the closest existing precedent) before a Plan agent produced a full design. Mid-plan, exploration corrected the parent's initial assumption: the async boundary belongs in the **Server layer** (`sessionAnswer`), not in `telegram.go` — keeping `Poll`, `t.answer`, and all of `telegram_test.go` untouched, since `t.answer` stays synchronous and just returns in milliseconds (enqueue + empty reply = the poller sends nothing).

Mid-session the user layered a second requirement on top of the queue design: "When the session is running a long thinking and the user sends a message starting with ! it will [stop] the current waiting, get the result and execute the message... immediately." That became the `!`-prefix interrupt: cancels the in-flight run via a per-task `context.WithCancel`, delivers nothing (no partial output exists — the vendor CLIs are non-streaming), and pushes the new message to the front of that session's queue; a bare `!` just stops.

Implementation followed TDD end to end across `server/store.go` (new `unread` column + `Append/ClearSessionUnread`), `server/chat.go`/`server/answer.go` (split `ChatAnswer` into a session-taking `chatAnswer` core so a queued message re-resolves its *bound* session, never the live active pointer), new `server/queue.go` (per-session FIFO drainer: `enqueue`/`drain`/`runTask`/`typingOwner`), `server/cron.go` (`notifyOwner` generalized to take a `tgReply` so completion notices can carry a resume button), and `server/command.go` (`sessionAnswer` now enqueues and returns instantly, `/agent <task>` acks with "⏳ running", `resumeSession` delivers and clears `unread`, `/sessions` gained ⏳/✉ markers). Tests updated across `chat_test.go`, `answer_test.go`, `command_test.go`, `agent_test.go`, `pairing_test.go`, plus a new `queue_test.go`. `go build`, `go vet`, and `go test -race -count=2 ./...` all passed. `wiki/tasks.md` was updated with the new top deferral (queued-but-unstarted messages die on restart — accepted, marked with a `ponytail:` comment on `sessionQueue`). Full design recorded in [[decisions/background-session-queue]]. The user then said "commit this."

Immediate follow-up, a new standing rule: "Always remember to bump the version when we add a new feature or new bugfix." Applied retroactively on the spot — `version/version.go` bumped v0.4.0 → v0.5.0, since the just-shipped background-queue feature hadn't been bumped yet (and CI's PR version gate would otherwise have blocked it). The rule was saved both to the assistant's own persistent memory and to the project wiki as [[rules/bump-version-on-ship]].
