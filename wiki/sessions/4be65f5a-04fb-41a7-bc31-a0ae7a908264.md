# CI fix for the /clear PR — dash's `echo` strikes again (2026-09-04, 08:37–08:46)

Opened with a status check: a phone-based Claude Code session had already implemented `/clear` (see [[decisions/telegram-clear]]) on branch `claude/telegram-clear-messages-w189jl` and opened PR #1, but its CI checks were failing — the ask here was purely "why, and fix it," pointing at `https://github.com/johnvilela/omni/pull/1`.

Diagnosed via `gh pr view`/`gh run view --log-failed`, then checking out the branch locally to reproduce: unrelated to `/clear` itself. `TestPlanCronDone` (`server/plan_test.go`) fakes the `claude` CLI as a `#!/bin/sh` script built with `echo '{"result":"trained today\nPLAN DONE",...}'`. On the dev machine (Arch), `/bin/sh` is bash, whose `echo` leaves `\n` literal, so the JSON parsed fine locally. On Ubuntu CI, `/bin/sh` is dash, whose `echo` expands `\n` into a real newline byte, breaking the JSON with `invalid character '\n' in string`. This is the exact same bug class as [[gotchas/dash-echo-mangles-backslash-escapes]] (`TestAgentAnswerSendFile`, an earlier session) — a second, independent test fixture hit the identical dash-vs-bash `echo` divergence, found this time via a targeted `grep` for `echo .*\\n` across the test suite.

Fixed by swapping `echo` for `printf '%s\n'` in the fixture (never escape-expands on any POSIX shell), verified locally by re-running `TestPlanCronDone` under `-race` and the full suite, then committed `f55744d` and pushed to the PR branch. Also wrote the finding up as its own wiki page, `gotchas/dash-echo-expands-backslash-n.md` (committed `110c1ac`), generalizing the rule for future test-generated shell fakes rather than leaving it as a one-off comment.

Watched `gh pr checks --watch` (with one retry after a short sleep) until both `test` and `version-check` came back green. Session ended with the PR ready to merge — not merged in-session, left for the user to do when ready.
