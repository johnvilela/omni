Opened with a screenshot of a failed CI run for `TestAgentAnswerSendFile` ("What happened here?"). Diagnosed before being asked to fix: the test fakes the `claude` CLI as a `#!/bin/sh` script built with `echo '<json containing a \n escape>'`. On the dev machine `/bin/sh` is bash, whose `echo` prints the backslash literally, so the `\n` stayed a valid two-character JSON escape and the test passed locally; on Ubuntu CI `/bin/sh` is dash, whose `echo` expands `\n` into a real newline byte, breaking the JSON (`invalid character '\n' in string`). Verified identically under alpine's POSIX `sh` via docker. User said "fix this": replaced `echo` with `printf '%s\n'` in the fixture (`server/agent_test.go`), bumped version to v0.10.1, full suite green, committed `8d5b3c4`. Recorded as [[gotchas/dash-echo-mangles-backslash-escapes]].

After a `/compact`, asked "What do you suggest to work next?" — answered from the codebase's own `ponytail:`-marked ceilings, ranked: (1) persist the message queue (highest risk — a Telegram message accepted then dropped on restart), (2) `/pin`'s 5-newest-only session list can drop an older unread session, (3) `read_file` results land a turn late. User: "execute the 3" — all three implemented in one pass:

- New sqlite `queue` table (`AddQueued`/`DeleteQueued`/`QueuedMessages`); `enqueue`/`preempt` persist a row, `drain` deletes it the instant a task starts (the user turn itself then persists in `messages`); `replayQueue()` runs at boot and re-enqueues whatever rows a dead server accepted but never ran.
- `RecentSessions` reordered to `(unread != '') DESC, id DESC` — fixes both the `/pin full` dashboard and the `/sessions` keyboard in one query change.
- `chatAnswer` detects a `TOOL:read_file` line in the reply, applies it, and — if it fired — runs one follow-up llm round with the file content already in view, returning only that round's answer while history keeps both; capped at one follow-up round.

Shipped as v0.11.0, full suite green including `-race`, committed `179fefb` — "feat(server): persist queue, float unread sessions, same-turn read_file". Full design folded into [[decisions/background-session-queue]].

Next ask: "the omni guardian should check sometimes a day (not every time) if some packages related have update, for example, if i have release a new version of Memoria." Mid-turn correction: "Not all packages should be checked" — pivoted away from a hardcoded tool table to an owner-curated `update_repos: [owner/name, ...]` list in config.yaml; empty/absent disables the check. Implemented: a 6h throttle tracked by an `updates.stamp` file's mtime (deliberately not a `guardian.json` key, since `omni doctor`/`omni guardian` render every key there as an active alert); installed version parsed from `<binary> --version` (binary name = repo basename; omni itself special-cased to the compiled-in `version.Version` since the CLI has no `--version`); numeric `semverLess` comparison so a local source build ahead of the latest release never alerts; any failed GitHub lookup is indeterminate (previous alert state kept, never a fake recovery). Shipped as v0.12.0, committed `f1adef6` — "feat(guardian): alert when watched github repos release newer versions". Full design in [[decisions/guardian-update-watch]] (a first `memoria_write_page` attempt at a top-level `install.md` edit was rejected with "path outside the wiki structure", so the design landed as a new `decisions/` page instead).

Main feature of the session: "Lets add a way to approve, deny or ask edit a AI plan/action before execute it. It must work on the normal flow because the agent mode is the yolo mode and accepts everything." Two Explore agents (Telegram UI capabilities: inline keyboards/callbacks already exist; agent execution flow: the only `exec.CommandContext` is `runCLI`, fully buffered, no streaming, agent mode's only "approval" was unenforced prose in the workspace seed) plus a Plan agent produced the design, refined mid-plan by "If a tool request permission, i must have the option to approve and add it to the whitelist." Delivered close to the plan: privileged `TOOL:` lines in a normal chat reply (never agent mode) park as a `proposals` sqlite row instead of executing, pushed to the owner with ✅ approve / ✅ always (approve + whitelist) / 🚫 deny / ✏ edit buttons; gate checked on both llm rounds in `chatAnswer` (the read_file follow-up round is untrusted input too); all-or-nothing per reply since TOOL lines execute in order; config `approvals: off` / `approval_tools` / `approval_skip` (a string, not bool, so the zero config value fails safe to gate-ON). Shipped as v0.13.0. Full design in [[decisions/chat-tool-approval-gate]].

Immediate follow-up in the same session: "Can we add the API wrapper that doesnt exists yet? not just for this, but for other interactions too" — pointed at a ceiling the Plan agent had flagged (tapped proposal buttons stayed visibly live forever, since `editMessage` had no keyboard support). Added `editMarkup` (wraps `editMessageReplyMarkup`), gave `editMessage` a keyboard parameter, and gave `tgReply` two general-purpose flags any button handler can set: `StripKeyboard` (remove the tapped message's buttons after handling) and `Edit` (replace the tapped message in place instead of posting a new one). Applied immediately to two interactions: approval taps now strip their buttons, and `/crons`' 🗑 delete now re-renders the listing in place instead of leaving a stale list behind. Resume buttons were left as-is on purpose (they stay valid and reusable). Shipped as v0.14.0.

Both the approval-gate feature and the telegram wrapper landed together in one commit, since neither had been committed individually yet: `/git-commit` → `07a18b5` — "feat(server): gate privileged chat tools behind owner approval buttons" (16 files).
