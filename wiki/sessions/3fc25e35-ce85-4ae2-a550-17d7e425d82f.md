# Chatbot memory: evaluation, plan, implementation, and bare-CLI answers (2026-09-01)

Started as a pure evaluation, no code changed: "Do not change anything yet, we are just evaluating things." Confirmed the bot had zero memory by design — `server/answer.go` stated "Single-turn, no history": every Telegram message was answered from scratch, both on the oauth/CLI path (`codex exec` / `claude -p` / `gemini -p`, a brand-new session per call) and the api_key path (`askAPI`, one message, no system prompt). Discussed OpenClaw's two-layer model (short-term: one long-lived agent session per chat, full transcript replayed and compacted; long-term: curated `MEMORY.md`/`memory/*.md`) and concluded `johnvilela/memoria` (this project's own memory system) was the layer-2 analog only, not a fit for "what was the previous message" — it captures coding-agent sessions via hooks into a project wiki, with no mechanism for arbitrary Telegram turns.

Follow-up questions settled the short-term design: a per-chat message buffer in the existing SQLite store, not markdown (markdown called out as the worst option; JSONL named as the acceptable file-based alternative). Capping decided by token budget rather than message count (chars/4 heuristic, chars/3.5 for Portuguese, walking history newest→oldest until a 4-8k token budget is hit) — exact tokenization considered and rejected as unneeded latency/dependency for a personal bot. `codex exec resume`/`claude -p --resume` was considered and rejected too (it would hand session/compaction ownership to each vendor CLI, with per-provider plumbing to babysit).

The session resumed the same day with the concrete ask to plan and build: memoria as the long-term layer, uuid7 session identity, and a short human name per session for a future "resume old session" command. Two exploration agents ran in parallel to ground the plan: one mapped omni's own store/CLI/config internals (extending SQLite is trivial; only `fromID`, not `chat.ID`, is threaded to the answer path, but `from.ID == chat.ID` for 1:1 DMs so keying on it needs no plumbing changes; `google/uuid` was already an indirect dependency via the sqlite driver and has `NewV7()`), the other dug into memoria's global-mode and non-interactive surface (findings recorded in [[gotchas/memoria-write-is-mcp-only]]). Mid-design the user added a forward-looking constraint: "On the future we will create our on hooks, like claude code or codex, the Memoria will attach to it" — shaping the plan's three seams (`ensureSession`, `nameSession`, `onCompaction`) as the intended future attachment points rather than adapting memoria's own hook model to Telegram turns now. A Plan agent then produced the full implementation design, now recorded in [[chatbot-memory]].

Implementation followed the plan's TDD red-first order end to end: `server/store.go` gained the `sessions`/`messages` tables and accessors; `server/chat.go` (`composePrompt`, `tokenBudget`, `estTokens`, `ensureSession`, `ChatAnswer`, `nameSession`) and `server/memory.go` (`memoriaWiki`, `stripFrontmatter`, `readMemory`, `writeMemory`, `onCompaction`) were written test-first; `server/answer.go` was edited to retarget `answerNotice` at `ChatAnswer` and move the `"(empty reply)"` substitution out of the low-level `Answer`; `server/config.go` gained `token_budget`; `server/api.go` gained the `digesting` in-flight guard. TDD caught one real bug: the background session-naming goroutine collided with the next message's queries (SQLITE_BUSY) — fixed at the root in `OpenStore` with `SetMaxOpenConns(1)`, documented in [[chatbot-memory]]. `go mod tidy` promoted `github.com/google/uuid` to a direct dependency (see [[dependencies]]). The full suite, `go vet`, and `gofmt` finished clean; `wiki/chatbot-memory.md`, `wiki/index.md`, `wiki/api.md`, and `wiki/dependencies.md` were written/updated and the version bumped to `v0.3.0`. `memoria bootstrap --global` was run and succeeded — global mode is now on for this machine, so the long-term memory layer is live, not just designed.

Immediately after, a new ask in the same session: "Can we make the CLIs we are using make use of no tool or MCP? because we will inject your own tools and MCPs." Added `cliArgs` in `server/answer.go` to build every vendor-CLI invocation (both the `oauth` and `claude-code` paths), with the exact argv per CLI locked by a new `TestAnswerCLIBare`. Live-verified against the real CLIs while tuning flags: codex and claude both answered correctly bare; gemini needed `--allowed-mcp-server-names omni-none` specifically because an empty allowlist name is rejected (`Invalid policy rule: mcpName is required`). One concrete finding: claude's `--setting-sources ""` flag turned out to be load-bearing, not just belt-and-suspenders — without it, the operator's own global settings were reaching into bot answers (a global SessionStart hook was firing inside every reply). A second, unrelated finding surfaced during the same live-testing: the gemini CLI login on this machine is currently rejected by Google (`IneligibleTierError`), independent of the new flags — recorded as [[gotchas/gemini-oauth-ineligible-tier]]. Full contract detail lives in [[api]].

The session ended with the user saying "commit this", then explicitly invoking `/git-commit the new changes`. The git-commit skill staged the feature files (`go.mod`, `version/version.go`, `server/answer.go`, `server/answer_test.go`, `server/api.go`, `server/config.go`, `server/store.go`, `server/store_test.go`, `server/chat.go`, `server/chat_test.go`, `server/memory.go`, `server/memory_test.go`, `wiki/chatbot-memory.md`, `wiki/api.md`, `wiki/dependencies.md`, `wiki/index.md`) and committed as `f1a625d` — "feat(server): give the telegram bot short- and long-term memory" (16 files, +967/−20). Memoria's own bookkeeping pages (`wiki/sessions/*`, `wiki/gotchas/*`) were deliberately left unstaged, to be committed separately via `memoria commit` or a follow-up `/git-commit`.
