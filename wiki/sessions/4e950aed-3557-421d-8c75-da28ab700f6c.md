A long session (one `pre-compact`/`post-compact` boundary in the middle) that shipped two unrelated features back to back: the `/pin` telegram dashboard, then full photo/document exchange plus a chat-mode file toolkit born from three live bug reports. Full technical detail for both now lives in [[decisions/pin-dashboard]] and [[decisions/telegram-media]]; this page is the narrative of how they came about.

## `/pin` status dashboard (v0.7.0)

Opened with: "Lets create command on telegram that will pin a message that will be update time from time with the information of how many running sessions are on the background and the currently active session... keep in mind that we must keep this message clean to better UX." Two Explore/Plan agent rounds mapped the telegram client, session/queue internals, and produced a full design before any code was written. Refined through two `AskUserQuestion` rounds: update mode = event-driven (no ticker), content = a counts line plus an optional session list ("clean version with just the counts line or a complete version with the session list"), lifecycle = a toggle command, and clean/full switching = a command arg (`/pin full` / `/pin clean`) rather than an inline button.

Implemented exactly as planned on the first pass — `server/pin.go` (new), five one-line Telegram primitives added to `telegram.go` (edit/pin/unpin/delete/send-returning-id), a `pins` SQLite table in `store.go`, and ~10 one-line `refreshPin()` hooks scattered at the actual state-change points (`queue.go`, `command.go`, `chat.go`, `api.go`'s `ConnectTelegram`). `go build`/`vet`/`test -race -count=2` all green on the first try — no bugs hit during implementation. Version bumped to v0.7.0, `wiki/api.md` and the new `wiki/decisions/pin-dashboard.md` written, `scripts/dev.sh` re-run and verified live (`curl localhost:8788/status` → v0.7.0). Committed as `815ea1e` — "feat(server): add /pin pinned telegram status dashboard with event-driven refresh" (12 files, +531/−16). A `pre-compact` boundary followed immediately after.

## Telegram media exchange, in four rounds of live bug reports

Post-compact, a new ask: "be able to receive photos i sent on telegram BUT also send photos to me... i asked Omni to update my linkedin profile and it answered me with a print showing the change screenshoted and some text. I must be able to send some documents too and able to receive documents too." Two Explore agents (one for the existing telegram/session flow, one specifically re-verifying facts before the Plan agent) confirmed the update struct decoded text only, the Telegram struct discarded the bot token after building its base URL, and the only agent→omni channel was the existing `TOOL:` line protocol (`server/tools.go`) used by cron jobs — the plan reused that pattern rather than inventing an MCP server or HTTP endpoint.

**Round 1 (v0.8.0), built clean:** `server/telegram.go` gained photo/document decoding, `getFile`+HTTP download, and multipart upload; `gatedAnswer` was split so a new `gate()` helper could run before file downloads too (no download for unpaired senders); new `server/media.go` handled inbox saves and a `TOOL:send_file` executor wired into `agentAnswer` and cron agent runs. Verified live end to end (agent session read an inbox photo, sent a document back) and committed later together with everything below.

**Round 2 (v0.9.0) — "it worked indeed, but are we able to make this work without being on agent mode? Look at this screenshot: it was able to create the file but didn't send it to me."** Diagnosed by querying the SQLite `messages` table directly: the request had landed in a plain **chat session**, and `/home/jv77/sample.txt` never existed on disk — the bare chat LLM had **hallucinated** the file creation, since chat sessions have no tools by design. Fix: gave chat sessions a real server-side file toolkit — `write_file`/`read_file`/`edit_file`/`delete_file`/`send_file` as `TOOL:` lines, same execution pattern as the cron tools, plus an honesty rule injected into the chat prompt so the model states it has no shell/disk access instead of inventing results.

**Round 3 (v0.9.1) — "make the tools always manage files on a folder inside the .config/omni."** All five chat tools (and the inbound-file save path) jailed to `~/.config/omni/files` (`resolveJailed`): relative paths join it, absolute paths must already live inside, `..` escapes refused. Agent-mode `send_file` deliberately left unjailed — the agent already has full PC control.

**Round 4 (v0.9.2) — "I think it didnt work. Look at the answer on the screenshot" / "Still not working, but the message was readable now."** Two more real incidents in immediate succession: a chat model `read_file`'d a JPEG and dumped ~8KB of raw bytes into the chat (fixed with a text-only/binary refusal check — NUL byte or invalid UTF-8 → `⚠ binary` pointing at `analyze_file`/`/agent`), and then the resulting honest "I can't view images, use /agent" refusal was itself judged unsatisfying by the owner — the actual ask was for "explain this image" to just work from plain chat. Solved with a sixth tool, `analyze_file {path, question}`: a one-shot fresh-context agent run (same machinery as cron agent jobs — `agentProvider()` + `runClaudeAgent`/`runCodexAgent`, usage recorded, no session rows) whose answer replaces the `TOOL:` line directly, so a plain chat session can ask about an image or PDF without switching to `/agent`.

Each round was verified live against the real dev bot (`scripts/dev.sh` + a real Telegram photo/message) before moving to the next, and each bumped the version (v0.8.0 → v0.10.0) per [[rules/bump-version-on-ship]]. Wiki (`wiki/api.md` and `wiki/decisions/telegram-media.md`) was updated incrementally across all four rounds. `/git-commit` at the end staged all of it as one commit, `c976f73` — "feat(server): add telegram media exchange and jailed chat file toolkit" (18 files, +1142/−34) — covering rounds 1–4 together since none of the earlier rounds had been committed individually. Session ended right after the user said "push it"; the push outcome was not observed before the session closed (branch was 8 commits ahead of `origin/master` at commit time).

See [[decisions/pin-dashboard]] and [[decisions/telegram-media]] for the settled technical design of both features, and [[api]] for the current command/behavior reference.
