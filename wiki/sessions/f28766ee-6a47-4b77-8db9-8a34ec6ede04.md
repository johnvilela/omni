Opened with a concrete ask: build two new telegram commands — `/plan` (an interview in the chat session, saved to a wiki/SQLite-backed plan; a `#long` tag marks a plan spanning multiple days, broken into daily actions with periodic progress checks against the target) and `/memory` (save durable owner information to the wiki as "highest level" info) — both requiring the LLM to send a summary the owner can approve, deny, or ask to change before anything is saved. The open invitation to refine ("Ask me anything to refine this") was answered mid-design with one concrete correction from the user: "An approved plan is saved but it does not start by default, i must ask to execute a plan" — this is what split the design into a save-only `plan_save` tool plus a separate, also-gated `plan_start` tool.

## Design process

An Explore agent ran a single very thorough pass over the whole codebase before any design was attempted — the 5-touch-point pattern for wiring a new slash command (`command.go` switch → handler → `registerCommands` → the `want` test fixture → version bump), the three distinct LLM-interaction paths (single-shot `Answer`, chat sessions, agent sessions), the `TOOL:` protocol and where its contracts get injected, who writes to `wiki/` (nobody in Go code — it's the memoria MCP; the only Go code touching *a* wiki is `server/memory.go`, and that writes memoria's *global* wiki via plain file IO, not this repo's `wiki/`), the SQLite schema and its additive-migration pattern, both existing approval/confirmation UI shapes (the persistent `proposals` gate and `ops.go`'s ephemeral restart confirm), and the cron/task scheduling machinery — producing a full checklist for adding `/plan` and `/memory` before any decisions were locked in.

A Plan agent then re-read every function the leanings depended on (`proposeTools`, `runProposal`, `fireCron`, `chatAnswer`, `gatedCallback`, `runTool`, the store DDL, and four test fixtures) and validated/corrected five assumptions before writing the plan — notably: `task.go` already defines a `planPrompt()` function, forcing the new always-on section to be named `planContract()`; `parseControl`'s verb whitelist can't be reused for a `PLAN DONE` signal (needed its own last-non-empty-line check); and `TestChatAnswerInjectsPersona` asserts the persona leads the composed prompt, so the new core-memory section had to be a sibling, not a prefix ("HIGHEST priority" became prose in the section body, not position).

## Implementation

Followed the plan closely, with test-fixture updates threaded through as signatures shifted mid-build — `applyTools`/`runTool` grew a `sessionID` parameter, requiring a batch of `sed` fixes across existing test call sites. The `/memory` design shipped materially richer than the plan agent's original single-page draft: instead of one flat `core.md`, it landed as a themed system — `omni-bot/core/<theme>.md` pages, `general` always injected whole, other themes shown only as a name+count index until a free `memory_load` tool call sticks a theme to the session (`sessions.themes`), keeping e.g. family facts out of a work chat. Full technical design (both commands, the gated tools, the daily-plan cron mechanics, the themed memory system) is recorded in [[decisions/plan-and-memory-commands]], written to the wiki mid-session — this page reuses the [[decisions/chat-tool-approval-gate]] proposal/buttons flow end to end and the [[decisions/long-tasks]] task loop for non-`#long` plan execution.
