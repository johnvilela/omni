# Long-task checkpoints, a SQLite migration check-in, and the personality config command (2026-09-03, 11:46–13:03)

Opened with a detailed feature ask: let omni execute long multi-step jobs without losing context or hallucinating progress, using something like checkpoints stored in the wiki folder or SQLite. Two motivating scenarios: (1) feeding bank statements, credit card bills, and recurring-bill notes to `johnvilela/pecunia` (an MCP-equipped personal-finance CLI) and having omni set up its initial data — a long, token-heavy job; (2) a LinkedIn/freelance job search producing 15+ candidate postings. Requirements spelled out up front: run without `/agent` mode, support multiple subagents (capped at 4), record their output, track how many are running, hit a goal, checkpoint progress, then start the next step — and share a tool set between `/agent` and native chat rather than building two systems.

Two Explore agents mapped the codebase (existing `fireCron` agent pattern, the approval gate, `notifyOwner`, pin/callback plumbing) before a Plan agent produced a full design, followed almost verbatim: a deterministic Go loop (`server/task.go`) drives fresh-context one-shot agent runs against a markdown checkpoint (`agentDir()/tasks/<id>/task.md`) that the agents themselves maintain with their native file tools — the server never parses it. A new SQLite `tasks` table holds only orchestration state (status/step/note). Each step run ends with a control line the loop parses (`CONTINUE`/`DONE <summary>`/`BLOCKED <question>`/`FANOUT <n>`); fan-out work runs under a global semaphore capped at 4 concurrent agent runs across all tasks; `/task`/`/tasks` telegram commands drive pause/resume/cancel and steering (`/task #3 <text>` appends an owner note to the checkpoint and resumes a blocked/paused task); `resumeTasks()` restarts any task left `running` at boot, right after `replayQueue()`. Pecunia integration needed zero omni-side code beyond this — step agents already run un-bare, so registering pecunia's MCP in the vendor CLI config is enough.

Built TDD end to end (store methods, the loop with control parsing, fan-out, telegram surface, tool/approval/agent-contract wiring), full suite green including `-race`, and smoke-verified with a clean boot of a fresh server. Shipped as v0.15.0; full design and gotchas (pause-before-cancel ordering, chat-prompt-overhead test hardcoding, test-fake PATH restoration, the extended pinMu→qmu|s.mu|taskMu|store lock order) recorded in [[decisions/long-tasks]]. Committed as `a2e44ba` — "feat(server): run long tasks as checkpointed fresh-context agent loops" (19 files); the wiki pages were left for a separate `docs(wiki)` commit, done right after on request.

## SQLite migration check-in

A direct question followed: does the SQLite store have a migration system, and will upgrades keep an existing user DB intact? Confirmed yes — an additive-only, version-counter-free system already in place and already covering the new `tasks` table: new tables via `CREATE TABLE IF NOT EXISTS`, new columns on existing tables via a guarded `ALTER TABLE ADD COLUMN` list (duplicate-column errors on fresh installs ignored on purpose), tested by `TestStoreMigratesOldSchema` against an ancient pre-agent schema. Full detail now recorded in [[concepts/sqlite-migrations]].

## `personality` config flag (v0.16.0) and `omni config persona` (v0.17.0)

Next ask: a config flag to make omni's replies more direct and concise — "I have no patience to read long texts" — first proposed as `quiet_man` in the style of the caveman skill but more human-readable, then renamed mid-conversation to `personality` with three values: `normal`, `quiet`, `ultraquiet`. Scoped to config-file-only for this pass (no telegram toggle yet). Implemented as a single choke point in `readPersona()` (server/persona.go) that appends the style contract after the owner's AGENTS.md body, covering chat answers, cron `prompt` jobs, and `/context` token accounting with no other call-site changes; agent sessions get a one-line marker appended to the wire text only, keeping history in the owner's original words. Config is re-read every turn, so the change applies without a restart. Shipped as v0.16.0; full design in [[decisions/personality-flag]].

Immediate follow-up: turn this into a real command — `omni config persona`, an interactive select mirroring the `omni llm set-default` pattern, plus a `-p` flag to skip it. Delivered as a new `omni config` namespace (its own help screen, plus a root-help row) with a `readConfigKey` helper as the read-side twin of `saveConfigKey`. Live-smoke-tested against the built binary: `-p quiet` set correctly, `-p shouty` rejected with exit code 2 and config left untouched. Shipped as v0.17.0; command reference now in [[cli]]. Both the personality flag and the CLI command landed together in one commit, `43c9682` — "feat: switch reply personality via config and omni config persona" (9 files, spans server + cli, includes the v0.16→v0.17 bumps); the wiki pages from this stretch were left unstaged for a separate commit.
