# `omni llm model`: provider/model/effort picker, status display, and a mid-session bug hunt (2026-09-01, 21:44–22:23)

Continuing the LLM-provider work from [[sessions/18f39a98-4d2a-4686-86de-b307dfe4c7d8]], the user asked for a new `omni llm model` command: "-p" provider, "-m" model, "-e" effort flags, an interactive selection when a flag is omitted, and rejection of an invalid model. Two Explore agents mapped the CLI router (`cli/main.go`'s hand-rolled `switch args[0]`, no framework) and the existing llm plumbing (a hardcoded `llmModels` map in `server/answer.go`, no live model listing, `resolveLLM`'s oauth-before-key preference) before a Plan agent produced a full design that was then followed almost verbatim.

Implementation (TDD red-first): a new `GET /llm/{provider}/models` server endpoint lists a provider's models live from its API when an api key is in use (openai filtered to `gpt-*`/`o<digit>*`, gemini to `generateContent` models, `models/` prefix stripped) and falls back to a curated, hand-written `llmFallbackModels` list when the provider is oauth-connected (no key to query with) or the live fetch fails. `omni llm model [-p][-m][-e]` was added to the CLI router (inserted before the `llm-detail` catch-all), reusing the Bubble Tea picker pattern from `set-default` for provider and model selection; validates `-m`/`-e` against the served list and `low|medium|high` respectively; saves `<provider>_model` and an optional `<provider>_effort` to config.yaml. The picked model is now actually used: `askAPI` prefers `configuredModel(provider)` over the hardcoded default, and `cliArgs` appends it per vendor (`codex exec -m`, `claude --model`, `gemini -m`) — all three flag spellings confirmed against the installed CLIs. Along the way a real bug was found and fixed in `saveConfigKey`, recorded in [[gotchas/save-config-key-corrupts-int-keys]]. Full suite/`go vet`/`gofmt` clean, verified live against the dev server (`scripts/dev.sh`, curl, `omni-dev llm model ...`), and [[api]] updated with the new endpoint contract.

Immediate follow-up: "When i run the command 'llm' or 'status' should show the selected model and effort too." The server's `GET /llm` status JSON gained `model`/`effort` fields (read from config, omitted when unset); the CLI's `LLM` struct mirrors them; one change to the shared `renderLLM` covers `omni llm`, `omni llm <provider>`, and `omni status` since status reuses it: `● claude — connected (oauth) · claude-haiku-4-5 (effort high) ★ default`. TDD again (`TestLLMStatusModelEffort`, extended `TestRenderLLM`), verified live, [[api]] updated again.

A live bug report followed: "when i changed from claude to openai and asked the same question it returned the chat history and then the error. We have 2 things to fix here: first thing is whenever we got an error, the chat history should not be appended to it, we should return JUST the error. Second thing is: apparently I selected a model that does not exists on openai, why i was able to do this?" Two separate issues:

1. **Chat history leaking into error replies** — fixed at the root (touched `server/answer.go` and `server/llm.go`, locked in by a new `TestRunCLIErrorConcise`): an answer failure now returns just the `⚠` error text, never the composed prompt's history. Confirmed via full suite/`go vet`/`gofmt` and a live dev-server restart. [[api]] updated with this behavior note.

2. **A nonexistent model was accepted** — root cause traced to `-m` validation only checking membership in whatever list `/llm/{provider}/models` served; for openai (oauth-connected here via codex, so no live key to query) that's the curated `llmFallbackModels["openai"]` list written at plan time, never actually verified against `codex exec -m`. Live-probed candidate model names against the real `codex` CLI (`gpt-5.1`, `gpt-5.1-codex`, `gpt-5.1-codex-mini`, `gpt-5-codex`, `gpt-5`, `gpt-5.6-sol`, `gpt-5.6-sol-mini`, `gpt-5.6`, `gpt-5.5`, `gpt-5.6-codex`) and looked for a `codex models list`-equivalent (none found in `codex --help`) — every one of those guessed names, including `gpt-5` and `gpt-5.1`, got the same 400 from codex. The user then posted a screenshot of the models codex actually offers, which resolved it: codex on a ChatGPT login accepts ONLY the models from its own `/model` picker, not general openai API model names — so openai-via-oauth now serves its own dedicated list, `llmCodexModels` (`gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`, `gpt-5.5`, `gpt-5.4`, `gpt-5.4-mini`), and validation rejects anything else; disconnected/fetch-failure cases still fall back to the generic `llmFallbackModels`, api-key users keep getting the live-queried list. The user's own broken saved config (`openai_model: gpt-4.1`) was repaired to `gpt-5.6-sol` (codex's own default) and the exact bot invocation verified live. Full suite/`go vet`/`gofmt` stayed clean throughout. [[api]] was updated with both this behavior and how to re-verify the codex list when it inevitably goes stale (`codex exec --skip-git-repo-check -m <name> "reply with exactly: pong"`) — see [[gotchas/llm-fallback-model-names-unverified]] for the full postmortem on trusting curated fallback lists.
