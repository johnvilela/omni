Opened with a concrete feature ask, refined via an open invitation to ask questions: "Lets create a way to install plugins on omni, on the CLI the command will be like this 'omni plugins install {...}', the plugins must be Go package with MCP && skills. An example that will be used soon is: https://github.com/johnvilela/pecunia - i'll install it and start to manage my finances using omni to help. The 'omni plugins' will list all the installed plugins with a UI to remove it. The plugins can have some instalable telegram interface too, for example: installing pecunia will let me use commands like '/pecunia-today' or '/pecunica-cc', the pecunia itself does not have this yet, so you will need to write a documentation explaining how the packages will create this integration."

Deep exploration ran before any design: two agents mapped omni's own CLI/server/agent-mode architecture (no CLI framework, hand-rolled routing, chat mode locked bare via `TestAnswerCLIBare`, agent mode already un-bare with cwd = `agentDir()`) and the real `johnvilela/pecunia` repo (a Go CLI with a built-in `pecunia mcp` stdio server, skills under `cmd/skills/`, goreleaser release assets) before any code was written. AskUserQuestion settled the shape: install via GitHub release binary; Telegram commands are pecunia's own responsibility to define, not omni's job to generate; MCP+skills scope = agent workspace only; manifest = the binary prints it itself (`<bin> omni-manifest`). A Plan agent verified live against the installed vendor CLIs that claude's `--mcp-config` merges with user config and codex's `exec -c mcp_servers.*` TOML overrides work, then produced a full implementation plan.

The first `ExitPlanMode` was rejected with a correction: "the contract must be generic, the commands can be named anything. Pecunia was used as just an example of plugin" — this dropped an assumed plugin-name-prefix requirement for Telegram commands (kept only as a documented recommendation in PLUGINS.md) and added install-time collision refusal against built-ins and other installed plugins instead. The second plan was approved.

Implementation followed TDD: ~25 new tests across `cli/plugins.go`/`cli/plugins_test.go` (install/remove/list, GitHub release download + checksum verify + tar.gz extraction, `.mcp.json` merge preserving foreign entries, config-list read-merge-write), `server/plugin.go` (manifest loading, Telegram dispatch, sync endpoint), `server/agent.go` (`--mcp-config` for claude, `-c mcp_servers.*` overrides for codex), `server/context.go` (skill tokens counted from the agent workspace too), and `guardian/main.go` (a stale-plugin update alert now hints `omni plugins install <repo>` instead of the generic install.sh line). A live smoke test confirmed claude actually loads project-level `.claude/skills/` from cwd before finalizing the skills install path. `PLUGINS.md` was written as the generic contract doc for plugin authors, version bumped to v0.24.0, and the full technical design landed in [[decisions/plugin-system]]. Verified end to end against the real `johnvilela/pecunia` repo: the installer downloaded and extracted its real v0.4.0 release, then failed cleanly with "not an omni plugin (see PLUGINS.md)" — pecunia doesn't implement the manifest yet, and nothing was left half-installed. Deployed to the dev server and confirmed live: `/status` reported v0.24.0, `POST /plugins/sync` published successfully against the real Telegram bot.

`/git-commit` committed the feature as `5abe2cb` — but the working tree was still checked out on `claude/telegram-clear-messages-w189jl`, a leftover branch from an earlier session's `/clear` PR (see [[sessions/4be65f5a-04fb-41a7-bc31-a0ae7a908264]]), not `master`. Caught by the user: "You did this changes on other branch but the main. Move the plugin features into the main directly." Fixed by fetching origin (discovering PR #1 had already merged and released as v0.23.0, so local master was stale), resetting local master to `origin/master`, cherry-picking `5abe2cb` onto it cleanly as `bda6914`, and resetting the stale branch back to its own origin tip. Pushed to master on explicit confirmation ("yes") — this auto-triggered the release workflow (a push to master carrying an unreleased version bump *is* the release action), which succeeded: **v0.24.0** is live on GitHub with all six binaries (cli/server/guardian × amd64/arm64) plus checksums. Recorded as a process gotcha in [[gotchas/stale-branch-before-commit]].

## README, LICENSE, and GitHub metadata

After a `/compact` boundary, a new ask: "Add a README with a good UI/UX and the ASIIC logo on top. It must have a small description, a installation guide, a setup guide. Also the link to the plugins documentation. Also update the github description and add some topics too." An Explore agent confirmed the repo had no README (only the memoria-pointer `AGENTS.md`/`CLAUDE.md` and `PLUGINS.md`) and mapped the real setup flow (`scripts/install.sh` builds from source — git clone + `go test` + a `gum`-driven install, NOT a release downloader; setup is `channels connect` → `llm connect` → `llm set-default` → pairing approve → `omni doctor`) before writing anything. Delivered `README.md` (an ASCII-shadow OMNI banner reusing the CLI's own banner style, badges, description, features, requirements, the accurate build-from-source install guide, the 4-step setup guide, CLI + Telegram command tables, and a plugins section linking to `PLUGINS.md`) plus an MIT `LICENSE`, then set the GitHub repo description and nine topics via `gh repo edit`. Committed as `63cc10e` — "docs: add readme with install and setup guides + mit license" — and pushed; the release workflow ran and correctly skipped cutting a release since it was a docs-only change with no version bump. Full detail in [[decisions/readme-and-github-metadata]].
