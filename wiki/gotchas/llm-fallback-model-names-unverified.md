Found via a user bug report while testing `omni llm model` (see [[api]], [[sessions/4a8f703c-421a-438d-a77b-a6d786d01a6b]]): "apparently I selected a model that does not exists on openai, why i was able to do this?"

Root cause: `omni llm model -m` is validated only against whatever list `GET /llm/{provider}/models` serves. For an oauth-connected provider (openai here, via codex — no api key to query live models with), that list was the curated, hand-written `llmFallbackModels["openai"]` map written at plan time (`gpt-5.1`, `gpt-5.1-codex`, `gpt-5`, `gpt-5-mini`, `gpt-4.1`). Those names were guesses, never checked against what `codex exec -m` actually accepts — so a name from that list passed CLI/server validation and only failed later, when the vendor CLI was actually invoked.

Live probing against the real `codex` CLI (`gpt-5.1`, `gpt-5.1-codex`, `gpt-5.1-codex-mini`, `gpt-5-codex`, `gpt-5`, `gpt-5.6-sol`, `gpt-5.6-sol-mini`, `gpt-5.6`, `gpt-5.5`, `gpt-5.6-codex`) found every single guessed name — including `gpt-5` and `gpt-5.1`, which are real openai models — rejected with the same 400. `codex --help` has no `models list`-equivalent command, so there was no way to enumerate valid names programmatically.

**Resolution**: the user posted a screenshot of the models codex actually offers from its own `/model` picker. That revealed the real constraint: codex on a ChatGPT login accepts ONLY the models from its own `/model` picker — general openai API model names (`gpt-4.1`, `gpt-5.1`, etc.) get a 400 `not supported when using Codex with a ChatGPT account`, even when they're real, valid openai models. Fixed by giving openai-via-oauth its own dedicated fallback list, `llmCodexModels` (`gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`, `gpt-5.5`, `gpt-5.4`, `gpt-5.4-mini`), kept separate from the generic `llmFallbackModels` used for disconnected/fetch-failure cases; validation now rejects anything outside it. The user's own saved config (`openai_model: gpt-4.1`, now invalid) was repaired to `gpt-5.6-sol` (codex's own default) and the fix verified live against the real bot flow. Documented in [[api]], including the re-verification command for when the list inevitably goes stale: `codex exec --skip-git-repo-check -m <name> "reply with exactly: pong"`.

Rule of thumb: don't trust a curated fallback model list as verified — it's a best guess at plan time, not confirmed against the live vendor. For a CLI-mediated oauth provider (no models-list API to validate against), the vendor CLI can have its own narrower accepted-model set than the general provider API — verify candidate names against the vendor CLI/docs directly (or by screenshot from the vendor's own picker, as happened here) before trusting `omni llm model`'s validation to catch a bad one. codex has no list-models command, so `llmCodexModels` will drift over time and needs periodic re-verification the same way.
